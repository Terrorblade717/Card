# TON Arena — разбор архитектуры и план развития

## 1) Текущая архитектура (что есть сейчас)

**Backend (FastAPI):**
- `backend/main.py` содержит и API, и боевую логику, и хранение данных через JSON-файл. Инициализация FastAPI, боевой движок и API-эндпоинты расположены в одном файле.【F:backend/main.py†L1-L319】
- Данные игроков читаются и пишутся в файл `bot/players.json` при каждом запросе (функции `load_players`, `save_players`).【F:backend/main.py†L29-L54】

**Frontend (Telegram WebApp, статический HTML+JS):**
- Весь интерфейс и логика находятся в одном файле `backend/webapp/index.html`.【F:backend/webapp/index.html†L1-L476】
- Бой анимируется на фронте, но команда противника захардкожена, а события боя приходят с бэка (массив `events`).【F:backend/webapp/index.html†L250-L413】

## 2) Баги, уязвимости и неоптимальные решения

### 2.1 Баги и логические проблемы
1. **`BattleResponse` не содержит полей, которые реально возвращаются.**
   - В `start_battle` возвращаются `player_team`, `enemy_team`, `player_max_hp`, `enemy_max_hp`, но модель `BattleResponse` этих полей не описывает. При `response_model=BattleResponse` FastAPI их выкинет из ответа. Итог: клиент не может получить команды и max HP из API, хотя сервер пытается их отдавать.【F:backend/main.py†L17-L24】【F:backend/main.py†L258-L290】
2. **Использование общего mutable-значения по умолчанию.**
   - `events: List[Dict] = []` в `BattleResponse` — это общий список для всех ответов. Это потенциальный баг и память, которая «разделяется» между ответами. В pydantic нужно `Field(default_factory=list)`.【F:backend/main.py†L21-L24】
3. **Фронт не заполняет колоду по умолчанию.**
   - В `showDeckBuilder` выбранный герой в `<select>` отображается, но `currentDeck` может остаться пустым, если пользователь ничего не меняет, и `saveDeck` отправит пустую колоду. Это приводит к ошибке `Deck not set` при старте боя.【F:backend/webapp/index.html†L167-L217】
4. **Команда противника захардкожена на фронте.**
   - В `startBattle` создается `teamB` из фиксированного набора героев, а не из ответа сервера. То есть бой на клиенте и на сервере не синхронизированы визуально.【F:backend/webapp/index.html†L265-L298】
5. **Некорректная логика `debuff`.**
   - В `debuff` дважды вызывается `random.choice(enemies)`, т.е. броня уменьшается у одного, а ограничение `max(0, ...)` берется с другого. Скорее всего это баг — должен быть один и тот же враг.【F:backend/main.py†L112-L120】

### 2.2 Безопасность
1. **Полностью открытый CORS.**
   - `allow_origins=["*"]` разрешает любому домену делать запросы. Для Telegram WebApp лучше ограничить доменом WebApp/бота.【F:backend/main.py†L30-L38】
2. **Нет аутентификации пользователя.**
   - Пользователь идентифицируется по query-параметру `user_id`. Любой может подставить чужой ID. Для Telegram WebApp нужно проверять `initData` (HMAC-подпись от Telegram).【F:backend/main.py†L194-L290】【F:backend/webapp/index.html†L131-L146】
3. **Файл `players.json` открыт для гонок записи.**
   - При одновременных запросах возможна потеря данных. Отсутствуют блокировки или транзакции. JSON-хранилище — узкое место при росте пользователей.【F:backend/main.py†L41-L54】

### 2.3 Производительность и масштабирование
1. **Полная загрузка файла на каждый запрос.**
   - Каждый запрос читает и пишет весь JSON, что становится медленно при росте объема данных.【F:backend/main.py†L29-L54】
2. **Боевой движок и API в одном файле.**
   - Сложнее тестировать, расширять и поддерживать. При росте проекта нужно разнести на модули (battle, storage, api).【F:backend/main.py†L1-L319】
3. **Логика фронта монолитна.**
   - Весь UI и анимации в одном HTML; нет модульности, сложно развивать. Лучше отделить JS/данные/шаблоны.

## 3) Как правильно добавить анимации способностей

### 3.1 Добавить события «скилла» в backend
Сейчас события — это только `attack` и `execute`. Для красивых анимаций нужны дополнительные события (например `skill`, `buff`, `debuff`, `heal`, `stun`, `aoe`).

**Пример: расширение событий в боевом движке**
```python
# Пример события навыка в simulate_battle
if h.ability and h.silence == 0:
    h.ability(h, allies, enemies)
    events.append({
        "type": "skill",
        "hero": h.name,
        "ability": h.ability.__name__,
    })
```

**Зачем:**
- фронт сможет играть разные эффекты под конкретный `ability`.
- анимации не будут угадываться, а будут основаны на фактических действиях.

### 3.2 Отображение анимации на фронте
На фронте для каждого `event.type` можно иметь таблицу эффектов:
```js
const SKILL_ANIMATIONS = {
  taunt: { flash: '#ffd54f' },
  heal: { glow: '#4caf50' },
  aoe: { shake: true }
};
```

При обработке события `skill` использовать `ability` как ключ:
```js
if (ev.type === 'skill') {
  const fx = SKILL_ANIMATIONS[ev.ability];
  playSkillFx(ev.hero, fx);
}
```

**Важно:** визуал должен быть «детерминирован» по событиям сервера, иначе клиент будет рисовать то, чего не было в бою.

## 4) Подготовка к интеграции с TON Connect

### 4.1 Что нужно на фронте
1. Подключить `@tonconnect/ui`.
2. Вызвать `TonConnectUI.connectWallet()` при нажатии на кнопку.
3. Отображать адрес кошелька в UI.

### 4.2 Что нужно на бэкенде
1. **Проверка транзакций:**
   - Клиент отправляет «пруф» (payload) от TON Connect.
   - Бэкенд валидирует его (например, через TonAPI/toncenter).
2. **Хранение истории платежей:**
   - Минимум: таблица `payments` с `user_id`, `tx_hash`, `amount`, `status`.

### 4.3 Поток данных (пример)
1. Пользователь кликает «Купить +5 боёв».
2. Фронт формирует транзакцию и отправляет в кошелек.
3. Кошелек возвращает `tx_hash` → фронт отправляет его на сервер.
4. Сервер проверяет транзакцию и начисляет `extra_battles`.

## 5) Еженедельный сброс рейтинга и выплата TON

### 5.1 Как сделать reset + выплату
- Завести «сервисный» скрипт/джобу (cron или отдельный воркер), который:
  1. Снимает топ-10.
  2. Начисляет TON (через TonAPI/toncenter).
  3. Сбрасывает рейтинг.

**Минимальная архитектура:**
- Отдельный файл `jobs/weekly.py`.
- Запуск по cron раз в 14 дней.

**Пример (псевдокод):**
```python
players = load_players()
leaderboard = sorted(players.items(), key=lambda x: x[1]['rating'], reverse=True)
for i, (uid, data) in enumerate(leaderboard[:10]):
    payout_ton(uid, amount_for_place(i+1))
for uid in players:
    players[uid]['rating'] = 0
save_players(players)
```

### 5.2 Важные моменты
- Логи выплат должны храниться отдельно.
- Нельзя делать выплаты из процесса API, иначе вы рискуете зависанием.

## 6) Переход с JSON на SQLite/PostgreSQL

### 6.1 Когда переходить
- >1k активных пользователей или >=1-2 запросов в секунду.
- Появление платежей и рейтингов, где важны транзакции.

### 6.2 План миграции (без остановки)
1. **Добавить слой хранения:**
   - Ввести интерфейс `Storage` с методами `get_user`, `save_user`, `get_top_players`.
2. **Имплементировать JSON + SQLite параллельно.**
3. **Сделать миграцию данных в БД.**
4. **Отключить JSON, оставить только БД.**

### 6.3 SQLite как первый шаг
- Простая локальная БД, транзакции.
- Позже безболезненно мигрировать на Postgres.

## 7) Пошаговый план развития (от визуала до доната)

### Этап 1 — улучшение UI/UX
- Перевести `index.html` на структуру `HTML + отдельный JS + CSS`.
- Добавить модели героев с описаниями и иконками способностей.
- Обновить анимации: полет атакующего, эффекты умения, анимация статуса (stun/silence).

### Этап 2 — стабильность и корректность боя
- Синхронизировать события боя (от сервера к клиенту).
- Использовать `player_team` и `enemy_team` из API.
- Нормализовать `events` и добавить `skill`-события.

### Этап 3 — безопасность и Telegram WebApp
- Валидация `initData` из Telegram.
- Убрать `FAKE_USER_ID` и ввод ID только через Telegram payload.
- Ограничить CORS.

### Этап 4 — экономика и TON Connect
- Подключить TON Connect (front).
- Внедрить подтверждение транзакций (back).
- Начисление покупок: `extra_battles`, косметика.

### Этап 5 — рейтинг и сезонные награды
- Авто-сброс рейтинга раз в 14 дней.
- Выплаты топ-10 (cron/job + логирование).

### Этап 6 — переход на БД
- SQLite → PostgreSQL.
- Хранение истории боёв, транзакций, метаданных профиля.
